## 三、CLAUDE.md 必写模板

每个新项目的 CLAUDE.md 必须包含以下信息：

```markdown
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview
[一段话说清楚项目做什么、为谁做]

## Commands
[构建、测试、运行、lint 的具体命令——必须是可复制粘贴执行的]

## Repository Structure
[目录结构 + 每个顶层目录的一句话职责说明]

## Architecture
[模块关系和数据流向——用一张图或一段文字说清]

## Key Technical Facts
[技术栈特有的、不读代码就不知道的关键事实]

## AI / LLM Operations
[如适用：Provider、模型、Prompt 版本、eval 命令、CC Switch 路由、成本和权限边界]

## Known Issues
[已知技术债务、兼容问题、暂未解决的痛点，避免重复踩坑]

## Contribution Guidelines
[PR 前必须执行的命令、分支命名、Commit 规范]
```

**编写原则**：
- Commands 必须可复制粘贴直接执行，不要省略 `cd` 或 `activate`
- Repository Structure 只写顶层和关键子目录，不要展开每个文件
- Key Technical Facts 写"不读代码就不知道的事"，不写通用常识
- Known Issues 只记录真实存在的问题，不写猜测
- Contribution Guidelines 保持可执行，避免长篇流程说明

## 四、AI 辅助开发执行规则

本节用于约束 Claude Code / Cursor / Codex 等 AI 开发助手的项目内行为。工具专用规则文件可以从本节摘取同步，但不得制造与本规范冲突的第二套规则源。

### 4.1 启动检查（按任务范围执行）

AI 开始修改前，应先做与任务规模匹配的最小自检：

- 读取 `CLAUDE.md` / `AGENTS.md`、`README.md` 和与本次任务直接相关的配置文件。
- 涉及依赖、构建、测试时，读取 `pyproject.toml`、`package.json`、`pnpm-lock.yaml`、`uv.lock` 等真实配置。
- 涉及环境变量或外部服务时，检查 `.gitignore` 与 `.env.example`，不得读取、输出或复用真实密钥。
- 识别项目形态和既有目录模式，优先沿用现有架构，不为单次任务重塑目录。
- 如发现规则冲突，先按"规范优先级"裁决；冲突会影响安全、架构或破坏性修改时，必须向人类开发者说明并等待确认。

禁止为了形式完整而全量扫描所有文件、所有技能或所有规则。上下文应按需读取，避免把工具流程变成项目负担。

### 4.2 Skills 与规则加载

- 用户显式点名技能，或任务描述明显匹配技能触发条件时，才加载对应技能。
- 技能优先级：项目级技能 > 团队公共技能 > 全局默认能力。
- 加载技能时先读 `SKILL.md`，再按需要读取模板、脚本或示例，不批量展开整个技能目录。
- 技能不能覆盖系统、平台、权限和安全边界；发生冲突时，以更高优先级约束为准。
- 不自动从外部仓库更新技能缓存；升级技能属于依赖/工具链变更，必须由人类明确触发。

**外部技能安装原则**：
- 优先使用官方或可信来源，例如 OpenAI / Anthropic 官方 skills 仓库。
- 安装前必须验证 GitHub 仓库、路径和 `SKILL.md` 真实存在，不采信未经验证的清单链接。
- 只安装当前工作流确实需要、且与已有技能互补的技能；跳过重复、场景过窄或会引入额外凭证/外部服务依赖的技能。
- 第三方技能按供应链输入处理：先读说明和脚本，再决定是否安装；不得批量拉取未知技能目录。
- 技能安装后应记录来源和用途；需要生效的工具按各自机制重启或刷新索引。

项目若需要工具专用规则文件，可按以下方式维护：

| 工具 | 建议位置 | 说明 |
|------|----------|------|
| Claude Code | `.claude/assistant-rules.md` | 只放项目内 AI 行为规则 |
| Cursor | `.cursor/rules/000-global-rules.mdc` | 从项目规范同步核心约束 |
| Codex | `AGENTS.md` | Codex 以 AGENTS.md 为主要项目上下文 |

### 4.3 多智能体协作门槛

复杂任务应先拆分，但不强制所有复杂任务都启用多智能体。满足以下条件之一时，优先评估是否使用多智能体或并行角色：

- 涉及 3 个以上文件，或预计修改超过 100 行。
- 同时跨越前端、后端、测试、文档、部署等多个领域。
- 包含架构调整、权限模型、安全边界、数据迁移或外部发布。
- 需要独立审查、独立测试设计或多方案比较。

可选角色与产出：

| 角色 | 适用场景 | 产出 |
|------|----------|------|
| 架构 | 模块边界、技术选型、接口契约 | ADR、目录方案、API 契约、任务拆分 |
| 实现 | 业务逻辑、UI、接口、数据访问 | 可运行代码、类型定义、错误处理 |
| QA | 单元测试、集成测试、E2E、边界用例 | 测试用例、测试报告、缺陷清单 |
| Review | 规范、逻辑、安全、性能审查 | 按严重程度排序的评审报告 |
| Docs | README、API 文档、CHANGELOG、迁移说明 | Markdown 文档、示例、发布说明 |
| 协调 | 多任务整合、冲突处理、验收汇总 | 执行报告、验证结果、后续行动 |

多智能体不是默认姿态。如果一个模型能清晰完成任务，就优先本地执行；如果使用并行协作，最终必须整合为一个可验证结果。

### 4.4 代码生成与修改底线

- 严格遵循项目已有代码风格、架构模式和命名规范。
- 新功能必须配套测试；修复缺陷时优先补能复现问题的回归测试。
- TypeScript 禁止无理由使用 `any`；Python 关键边界应有类型标注。
- 用户输入、文件路径、外部回调、数据库参数和命令参数都视为不可信输入。
- 不硬编码密钥、凭证、令牌、私有源地址或真实个人数据。
- 不把样例、兜底、模拟数据伪装成真实成功结果。
- 大规模重构、破坏性迁移、远程提交、发布、强推、删除数据必须由人类明确确认。

### 4.5 输出与验收要求

AI 完成任务时，应清楚说明：

- 修改了哪些文件和行为。
- 运行了哪些验证命令，结果如何。
- 哪些验证未能运行，以及原因。
- 是否存在剩余风险、已知限制或需要人类确认的事项。

代码审查类输出必须先列问题，按严重程度排序，并给出文件位置、影响和修复建议。
