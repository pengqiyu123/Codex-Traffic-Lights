## 二、项目脚手架模板

根据第一节确定的项目形态，选择对应模板。

### 共同原则（所有形态适用）

- **按业务领域划分目录**，而非按文件类型
- **模块对外暴露有限接口**（`__init__.py` / `index.ts` / `mod.rs`）
- **配置、文档、测试各自独立目录**
- **敏感配置只放环境变量**，仓库只提交 `.env.example`，`.env` 必须写入 `.gitignore`
- **授权边界明确**，开源或对外分发项目必须包含 `LICENSE`；内部项目建议写明内部使用范围

### 2.1 本地工具（CLI / GUI 桌面应用）

适用于：自动化脚本、桌面工具、编辑器插件、数据处理管线。

```
project-root/
├── src/<package>/              # 核心代码
│   ├── __init__.py             # 对外 API 导出
│   ├── __main__.py             # CLI 入口（如有）
│   ├── models.py               # 数据模型集中定义
│   ├── workflow.py             # 主流程编排
│   └── <module>.py             # 按职责拆分（env / process / validator...）
├── tests/
│   ├── conftest.py             # 共享 fixtures
│   └── test_<concern>.py       # 按横切关注点分组
├── docs/
│   └── adr/                    # 架构决策记录
├── scripts/                    # 构建、打包、发布脚本
├── .env.example                # 环境变量示例（如需要）
├── pyproject.toml / setup.cfg  # 包配置 + 工具配置
├── CLAUDE.md
├── LICENSE                     # 对外分发时必须
└── README.md
```

**本地工具特有约定**：
- 入口只有两种：`__main__.py`（CLI）或主窗口类（GUI），不要分散多个入口
- 数据模型集中在 `models.py`，用 `@dataclass(frozen=True)` 不可变模式
- 外部依赖（进程、文件系统、API）封装在独立模块中，方便测试时 mock
- 错误用结构化异常类（`code: str` + `message: str`），面向用户的消息用项目目标语言

### 2.2 库 / SDK

适用于：被其他项目引用的共享包、客户端 SDK、工具库。

```
project-root/
├── src/<package>/              # 库核心
│   ├── __init__.py             # 公开 API（__all__ 导出）
│   ├── _internal.py            # 内部实现（下划线前缀）
│   └── <concern>.py            # 按关注点拆分
├── tests/
├── examples/                   # 使用示例（必须有）
├── docs/                       # API 文档
├── CHANGELOG.md                # 语义化版本变更记录
├── pyproject.toml / setup.cfg
├── CLAUDE.md
├── LICENSE
└── README.md                   # 必须包含 Quick Start
```

**库特有约定**：
- `__init__.py` 的 `__all__` 即为公开 API，新增导出必须在此注册
- 内部实现用 `_` 前缀标记，对外不可见
- `examples/` 目录必须包含至少一个完整可运行的示例
- 变更公开 API 是破坏性变更，必须经过评估
- 每次版本发布必须更新 `CHANGELOG.md`，并按 SemVer 标注新增、修复和破坏性变更

### 2.3 Web 全栈

适用于：Next.js、Nuxt、Django、FastAPI+HTMX 等——页面渲染和业务逻辑在同一代码库。

```
project-root/
├── src/
│   ├── features/               # 业务模块（每个功能独立目录）
│   │   └── <feature>/
│   │       ├── components/     # 模块内 UI 组件
│   │       ├── hooks/          # 模块内逻辑（hooks / composables / services）
│   │       ├── api/            # 模块数据获取
│   │       └── index.ts        # 模块对外接口
│   ├── components/ui/          # 全局基础 UI 组件（无业务逻辑）
│   ├── middleware/             # 全局中间件（鉴权、日志、租户识别等）
│   ├── lib/                    # 工具函数
│   ├── types/                  # 全局类型定义
│   └── config/                 # 配置
├── public/                     # 静态资源
├── tests/
├── .env.example
├── CLAUDE.md
├── tsconfig.json / pyproject.toml
└── README.md
```

**Web 全栈特有约定**：
- Feature 目录包含该功能的所有层次（UI + 逻辑 + 数据），不按技术层拆散
- 全局 `components/ui/` 只放纯展示组件，不含业务逻辑
- 状态就近管理：组件本地 → 页面级 → 模块级 → 全局，按需提升
- 全局状态必须有明确选型：React 可用 Zustand / Redux Toolkit，Vue 可用 Pinia；小型项目优先框架内置状态
- 禁止 `any`，用 `unknown` + 类型守卫

### 2.4 API 服务

适用于：纯后端 REST / GraphQL / gRPC 服务，无页面渲染。

```
project-root/
├── src/
│   ├── routes/ / controllers/  # 请求入口
│   ├── dto/                    # 请求/响应 DTO
│   ├── middlewares/            # 鉴权、限流、日志、错误处理
│   ├── services/               # 业务逻辑
│   ├── models/ / entities/     # 数据模型
│   ├── repositories/           # 数据访问（如果使用数据库）
│   └── config/                 # 配置
├── tests/
├── docs/
│   ├── adr/
│   └── api-contracts.md        # API 接口文档
├── .env.example
├── CLAUDE.md
└── README.md
```

**API 服务特有约定**：
- 依赖方向：routes/controllers → dto → services → repositories → models/entities，严禁反向
- Controller 不直接操作数据模型，通过 DTO 映射
- API 响应统一信封格式（status + data + error）
- 敏感接口添加频率限制（Rate Limiting）
- 中间件只处理横切关注点，不写业务流程

**统一响应示例**：

```json
{
  "status": "success",
  "data": { "id": "user_123" },
  "error": null
}
```

```json
{
  "status": "error",
  "data": null,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "用户不存在"
  }
}
```

### 2.5 多产品工作区（Monorepo）

适用于：多个应用/库共享同一仓库。

```
project-root/
├── apps/
│   ├── <app-a>/               # 应用 A（选择上述任一模板）
│   └── <app-b>/               # 应用 B
├── packages/
│   ├── shared-ui/              # 共享组件
│   ├── shared-utils/           # 共享工具
│   └── config/                 # 共享配置
├── tools/                      # 构建/分析脚本
├── pnpm-workspace.yaml         # pnpm workspace 配置（如使用 pnpm）
├── turbo.json                  # 任务编排配置（如使用 Turborepo）
├── CLAUDE.md                   # 顶层：工作区级约束
└── README.md
```

**Monorepo 特有约定**：
- 每个应用/包内部遵循对应的模板规范
- 共享包遵循"库 / SDK"模板规范
- 顶层 CLAUDE.md 写工作区级约束，子目录 CLAUDE.md 写应用特有约束
- 包之间优先使用 workspace 协议引用，例如 `workspace:*` 或 `workspace:^`
- 顶层只放跨包工具链配置；应用私有配置留在应用目录内

**pnpm workspace 示例**：

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

**turbo 任务示例**：

```json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**", ".next/**"] },
    "test": { "dependsOn": ["^build"] },
    "lint": {}
  }
}
```

### 2.6 跨语言适配说明

模板表达的是职责边界，不是固定语言目录。换语言时按生态惯例替换入口和模块目录：

| 生态 | 常见调整 |
|------|---------|
| Go | `cmd/<app>/` 放入口，`internal/` 放私有模块，`pkg/` 只放可复用包 |
| Rust | `src/main.rs` / `src/lib.rs` 放入口，模块用 `mod.rs` 或同名文件组织 |
| Java / Kotlin | `src/main/java` 与 `src/test/java` 保持标准 Maven/Gradle 结构 |
| .NET | 以 Solution + Project 划分应用、领域、基础设施和测试 |

只要依赖方向、测试位置、配置边界和公开 API 清晰，就不必机械复刻示例目录名。

### 2.7 AI / LLM 应用补充

涉及模型调用、RAG、Agent、MCP、Skills、Prompt 管理或多供应商路由的项目，基础目录沿用本章对应形态，并额外遵循 `06-AI产品专项规范.md`。

建议补充目录：

```text
project-root/
├── prompts/                   # 生产 Prompt、schema、模板
├── evals/                     # AI 功能回归样例和判分脚本
├── docs/ai/                   # 模型、RAG、Agent、路由和成本 ADR
└── observability/             # trace、usage、dashboard 配置（如适用）
```

**LLM API 接入底线**：
- LLM Provider 不散落在业务代码中，优先由统一配置层或网关管理。
- 本项目统一参考 `D:\python\JianYingPro\cc-switch-main`：Provider 管理、Codex/Claude/Gemini 接管、本地路由、故障转移、用量日志、MCP / Skills / Prompts 同步。
- Codex 接入 DeepSeek、Kimi、MiniMax、SiliconFlow 等 Chat Completions 兼容供应商时，必须通过 CC Switch 本地路由转换；不要把 `/chat/completions` 直接写入 Codex live 配置。
- Prompt、模型名、输出 schema、工具描述、reasoning / thinking 参数都视为可版本化配置。
- 新增 AI 功能必须有 eval 样例；能改变外部状态的 Agent 工具必须有人类确认点。
