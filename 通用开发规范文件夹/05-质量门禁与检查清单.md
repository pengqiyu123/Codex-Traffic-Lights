## 七、代码规模控制

### 7.1 核心原则：功能边界优先，数字只是信号

代码规模控制的目标是**可读性和可维护性**，不是追求某个行数指标。以下数字是参考信号，不是硬性上限——一个职责内聚的 400 行文件远好于两个各 200 行但互相耦合的文件。

| 指标 | 参考区间 | 超出时的思考方向 |
|------|---------|----------------|
| 单文件行数 | 功能内聚即合理 | 文件是否承载了多个不相关职责？如果是，按功能边界拆分 |
| 单函数行数 | 一屏可读（~40–60 行） | 函数内是否有可独立命名的段落？如果有，提取子函数 |
| 嵌套深度 | ≤ 3 层时心智负担可控 | 能否用 early return / guard clause / 策略对象平铺？ |
| 函数参数 | ≤ 4 个通常足够 | 是否有若干参数总是一起传递？提取为参数对象 |
| 圈复杂度 | ≤ 10 个分支可维护 | 能否用映射表、状态模式或策略对象替代 if-else 链？ |
| 单类方法数 | 按职责自然形成 | 是否存在两组方法从不一起使用？提取协作者类 |
| 单模块直接依赖 | ≤ 8 个通常可控 | 修改一个文件是否波及大量下游？引入门面或调整边界 |

### 7.2 何时拆分（按信号判断）

| 异味信号 | 推荐做法 |
|---------|---------|
| 一个文件包含多个不相关职责 | 按功能边界拆分为独立模块 |
| 函数内有段落注释标记步骤（如 `// 校验` → `// 执行` → `// 清理`） | 每个段落提取为命名清晰的子函数 |
| 嵌套超过 3 层，需要横向滚动或心理追踪才能理解 | early return / guard clause / 策略对象平铺 |
| if-else 链超过 5 个分支且都是同模式判断 | 映射表 / 状态模式 / 责任链 |
| 一批参数总是一起出现在多个函数签名中 | 提取为配置对象或参数字典 |
| 修改一个类时总需要同时修改另一个类 | 合并或重新划分职责 |

### 7.3 何时不拆（常见误拆场景）

- **按行数机械切割**：把一个内聚的函数拦腰截断，只因"超过 50 行"。拆分依据是职责边界，不是行号。
- **过度抽象**：为 2 行重复代码创建函数，而这两行在不同上下文有不同含义。重复本身不总是问题。
- **拆散相关逻辑**：把"数据校验"和"数据写入"分到两个文件，但它们总是一起修改。相关逻辑应就近放置。
- **"为了可测试性"拆分**：拆分后测试反而需要更多 mock，说明边界划错了。
- **生成代码强行控制**：自动生成代码、迁移文件、锁文件、大型配置文件自然超出参考区间，标记来源即可，不手工拆分。

### 7.4 三问判断法

遇到"要不要拆"时，用三个问题替代行数检查：

1. **改一个功能时，是否需要同时改这个文件里的不相关代码？**
   → 是：按功能边界拆分。
2. **新同事能否在 30 秒内找到"处理 X 的逻辑在哪里"？**
   → 不能：模块边界或命名有问题。
3. **删掉一个功能时，是否只需删一个目录/文件？**
   → 不是：拆分粒度可能不够。

### 7.5 平铺技巧速查

**early return**（消除嵌套）：

```ts
function submitOrder(order: Order) {
  if (!order.items.length) return fail("EMPTY_ORDER");
  if (!order.userId) return fail("MISSING_USER");

  return createOrder(order);
}
```

**映射表**（替代 if-else 链）：

```python
# ❌ 分支堆积
if status == "pending":   action = start_process
elif status == "running": action = check_progress
elif status == "done":    action = cleanup

# ✅ 映射表
STATUS_ACTIONS = {
    "pending": start_process,
    "running": check_progress,
    "done": cleanup,
}
action = STATUS_ACTIONS[status]
```

## 八、规范优先级

项目间发生冲突时，按以下顺序裁决：

1. **安全** — 不可妥协（密钥泄露、注入漏洞、权限缺失）
2. **架构** — 目录位置、依赖方向、模块边界
3. **类型安全** — 类型标注完整、禁止逃逸类型
4. **可维护性** — 功能边界清晰、职责单一（行数超出参考区间时检查职责是否混杂）
5. **命名** — 一致性比具体风格更重要
6. **风格** — 由格式化工具自动保证，不人工争论
7. **Git** — Conventional Commits 格式
8. **测试** — 覆盖率 ≥ 80%
9. **文档** — 关键决策有记录
