# 现代 AI 开发场景补充规范（择优整合版）

> 适用范围：包含 AI 辅助开发、LLM API、RAG、Agent、多模型路由、MCP / Skills / Prompts 管理的项目。
> 定位：补充本目录基础工程规范。本文聚焦 AI 产品上线和 LLM API 治理，不替代 `01`-`05` 的基础工程规范。
> 本地基准：本项目统一 LLM API / CLI 配置治理优先参考 `D:\python\JianYingPro\cc-switch-main`。

---

## 一、AI 项目形态先分级

开窗期先判断项目属于哪种 AI 形态，避免把所有项目都按 Agent 复杂度治理。

| 形态 | 特征 | 必做治理 |
|------|------|----------|
| AI 辅助开发 | 只用 Codex / Claude Code / Cursor 写代码 | AI 助手规则、验证命令、供应链规则 |
| AI 功能模块 | 总结、翻译、分类、文案生成 | Prompt 版本、输出 schema、回归样例 |
| RAG 系统 | 检索知识库再回答 | 数据来源、索引版本、引用、权限过滤 |
| Agent 系统 | LLM 可调用工具或改变外部状态 | 工具权限、人工确认、审计日志、kill switch |
| 多模型网关 | 多供应商、路由、降级、计费 | Provider 注册表、协议适配、健康检查、成本追踪 |

---

## 二、Prompt / Model 配置版本化

- Prompt、system message、工具描述、输出 schema、模型名、temperature、reasoning effort 都视为代码。
- 重复使用的 Prompt 放入 `prompts/`；一次性探索可以留在任务记录中，不强制作永久化。
- 生产 Prompt 必须记录版本、用途、输入输出契约和最近修改日期。
- 模型版本不得使用语义含糊的 `latest` 作为生产默认值；升级模型必须经过 eval 或回归验证。
- 不允许在线上静默改 Prompt 或模型配置；必须能回滚到上一版本。

建议目录：

```text
prompts/
├── system/
├── tasks/
├── schemas/
└── CHANGELOG.md
```

## 三、Eval 优先

AI 功能不是只靠单次人工体验验收。新功能至少准备一组可复跑 eval：

- 正常样例：主路径输入。
- 边界样例：空输入、超长输入、格式异常、多语言。
- 恶意样例：prompt injection、越权请求、敏感信息诱导。
- 回归样例：历史线上问题、用户纠错案例。

每个 eval 明确：

- 输入、期望输出或判分规则。
- 通过阈值：格式合规率、任务成功率、拒答正确率、幻觉率、工具误调用率。
- 失败处理：阻断发布、降级为人工审核、或记录为已知限制。

---

## 四、LLM Observability 与审计

LLM 调用必须可追踪，但日志必须脱敏。

建议记录：

- `trace_id` / `request_id`
- 用户动作或业务场景
- provider、model、prompt_version、schema_version
- 输入输出 token、cache token、费用、延迟、首 token 时间
- 工具调用、检索命中文档、外部写入结果
- 错误码、重试次数、降级或故障转移事件

禁止记录：

- API Key、refresh token、OAuth token
- 完整敏感 Prompt 或用户隐私
- 未脱敏的身份证、手机号、邮箱、地址、内部凭证

## 五、RAG 专项规则

- 知识库必须记录来源、版本、抓取时间、权限范围和过期策略。
- 回答必须区分“检索依据”和“模型推断”。
- 检索不到可靠依据时，应明确失败或提示需要人工确认，不得编造。
- Chunk 策略、embedding 模型、重建索引触发条件必须写入 ADR 或 `CLAUDE.md`。
- RAG 权限过滤必须在检索前执行，不只在回答后过滤。

## 六、Agent 工具权限分级

| 权限级别 | 示例 | 默认策略 |
|----------|------|----------|
| 只读 | 读文件、查日志、查数据库只读视图 | 可自动执行 |
| 本地可回滚写 | 修改工作区文件、生成临时文件 | 任务内允许，需最终 diff |
| 外部低风险写 | 创建草稿、更新测试环境 issue | 需说明目标与结果 |
| 外部高风险写 | 发邮件、发布内容、改生产配置、付款、删除数据 | 必须人工确认 |

Agent 系统必须具备：

- 工具 allowlist。
- 单任务预算和超时。
- 最大循环次数。
- 外部写入前确认点。
- kill switch 或停止条件。

## 七、LLM 安全专项

重点覆盖：

- Prompt injection：来自网页、文档、用户输入、检索内容的指令不得覆盖系统规则。
- 数据泄露：模型输入前做最小化和脱敏。
- 过度代理权限：工具只暴露任务所需能力。
- 不安全输出处理：模型输出不得直接拼 SQL、shell、HTML、正则或代码执行。
- 供应链风险：MCP server、skills、rules、agent 配置都要验证来源。
- 向量库风险：权限、租户隔离、删除同步和过期文档处理。

---

## 八、成本、限流与降级

- 每个 AI 功能定义预算上限、请求频率上限和最大重试次数。
- 简单任务可使用较低成本模型；高风险、高复杂度任务使用强模型并加强验证。
- 对稳定输入启用缓存；缓存命中逻辑必须不绕过权限检查。
- 降级路径要明确：换模型、换 provider、关闭非核心 AI 功能、转人工。
- 订阅制或额度制模型不得伪装成可精确 token 计费模型；计费口径要标注来源。

## 九、CC Switch 统一 LLM API 接入规范

本项目所有 LLM API / CLI Provider 接入优先使用 `D:\python\JianYingPro\cc-switch-main` 作为治理参考。它的定位不是业务 SDK，而是本地多 CLI、多供应商、多协议的配置和路由管理层。

### 9.1 接入边界

CC Switch 可统一管理：

- Claude Code、Codex、Gemini CLI、OpenCode、OpenClaw 等工具的 Provider。
- MCP、Prompts、Skills 的跨工具同步。
- 本地代理、故障转移、健康检查、请求日志和用量统计。
- Provider 配置的备份、恢复、导入导出和云同步。

业务代码不要直接依赖 CC Switch 的 SQLite 内部表结构；需要接入时通过配置导出、CLI 工具配置或明确的 API/脚本边界完成。

### 9.2 Provider 注册必填项

每个 Provider 至少明确：

- 名称、用途、供应商来源和官网。
- `base_url`，只填服务根地址，不手拼完整接口路径。
- API 协议：`anthropic`、`openai_responses`、`openai_chat`、`gemini_native` 等。
- 默认模型、可选模型列表、reasoning / thinking 参数。
- 是否必须走本地路由转换。
- API Key 存储位置和是否支持 OAuth / BYOK。
- 计费模式：token 单价、订阅、额度包或未知。

### 9.3 Codex + Chat Completions 供应商

Codex 当前按 Responses API 形态工作，而 DeepSeek、Kimi、MiniMax、SiliconFlow 等很多供应商提供的是 OpenAI Chat Completions 兼容接口。此类供应商不得直接把 `/chat/completions` 写入 Codex live 配置。

推荐链路：

1. CC Switch 接管 Codex，把 Codex 配置指向本地路由：`http://127.0.0.1:15721/v1`。
2. Codex 侧保持 `wire_api = "responses"`。
3. Provider 标记 `apiFormat = "openai_chat"`。
4. 本地路由把 `/responses` 转换为 `/chat/completions`，并转换请求体、SSE 和 usage 字段。
5. 路由将上游 Chat 响应转回 Responses 形态给 Codex。

验收方式：

- `~/.codex/config.toml` 指向本地路由。
- CC Switch 路由服务运行，且 Codex 接管开关开启。
- 切换 Provider 后重启 Codex 进程。
- 用 `/model` 或一次小请求确认模型与请求日志一致。
- 请求日志中出现 token、费用、延迟或错误状态。

### 9.4 本地代理与故障转移

本地代理默认监听 `127.0.0.1:15721`。启用接管时会改写各 CLI 的 live 配置，并备份原配置，停止代理时恢复。

代理治理要求：

- 生产或长期使用至少配置两个同类 Provider，才能开启故障转移。
- 设置请求超时、最大重试、熔断阈值和恢复窗口。
- 故障转移事件必须进入日志，不能静默切换后仍声称使用原 Provider。
- 不建议用本地路由代理官方 OpenAI Codex 账号，避免账号和合规风险。
- 端口、监听地址、接管状态和备份恢复流程必须可检查。

### 9.5 协议转换测试要求

新增 Provider 或协议转换逻辑时，至少覆盖：

- 非流式请求和流式 SSE。
- tool call / function call。
- system message、multi-turn history、reasoning / thinking 参数。
- `max_tokens` / `max_output_tokens` / `max_completion_tokens` 映射。
- usage 映射：input、output、cache read、cache creation、reasoning tokens。
- 错误映射：401、403、404、429、5xx、timeout。

### 9.6 用量与成本

统一记录：

- app 类型、provider、model、request_model。
- input/output/cache/reasoning token。
- 单价、倍率、总价。
- latency、first_token_ms、duration_ms。
- streaming 与非 streaming。
- data_source，避免 session 日志与 proxy 日志重复计数。

未知单价或订阅制模型必须标记为“不具备精确 token 成本”，不能自动补一个看似精确的美元成本。

## 十、上下文与快照

- 不强制每次任务生成上下文快照；跨天、跨会话、跨多人协作或长任务才需要。
- 快照建议放在 `.claude/snapshots/` 或项目约定目录，内容包括完成事项、修改文件、关键决策、验证结果、未解决问题。
- AI 修改前必须读取相关文件最新内容，不从旧上下文直接改。
- 禁止为“完整上下文”读取日志、构建产物、依赖目录、二进制和无关大文件。

## 十一、AI 生成内容追溯

- 不建议给每段 AI 生成代码都加注释，会污染业务代码。
- 追溯优先通过 commit、PR 描述、任务记录、生成日志和 review 记录完成。
- 合规要求强的项目可以在 PR 模板中增加“AI 辅助生成/审查”字段。
- 安全、权限、加密、支付、数据删除、生产运维代码必须人工重点审查。
